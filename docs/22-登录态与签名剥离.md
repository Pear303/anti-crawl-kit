# 22 · 登录态与签名剥离

> 一句话：**「拿到接口」不等于「能纯 HTTP」。**
> 必须用 `AntiRiskHttpClient` 重放一次，按返回码判断是 L1 直连、缺登录态，还是必须回浏览器。
>
> 这篇解决三个高频误判：
> 1. 把 XHR / GraphQL 当成一种「数据源」；
> 2. 在浏览器里请求成功，就以为纯 HTTP 也能成功；
> 3. 看到 `null` / `0` / `result != 1` 就以为「这个账号没数据」。

---

## 0. 先分清四组概念

| 概念 | 是什么 | 不是什么 |
|---|---|---|
| **XHR / fetch** | 浏览器发请求的传输机制 | 不是数据源，也不是接口协议 |
| **REST** | 多个固定端点，每个端点返回固定结构 | 不保证能纯 HTTP 重放 |
| **GraphQL** | 单一端点 + 查询语句，客户端指定字段 | 不是传输协议；也可以用 curl/Python 发 |
| **浏览器 XHR 拦截（L3）** | 打开页面，监听页面自己发出的请求，拿响应 JSON | 不是 DOM，也不是静态翻 JS |

关系：

```text
GraphQL 请求通常由 XHR/fetch 发出去
但 GraphQL 本身可以用 curl / Python / AntiRiskHttpClient 直接发
```

## 1. 路径分层：L0 ~ L4

| 层级 | 名称 | 做什么 | 成本 | 典型场景 |
|---|---|---|---|---|
| **L0** | JS 包找接口 | 下载 JS，找 baseURL / 路径 / 字段名 | 极低 | HTML 空壳、SPA |
| **L1** | 纯 HTTP | 直接请求接口或 HTML | 毫秒级 | 无签名、只需 Cookie |
| **L2** | SSR 状态 | 从 `__NEXT_DATA__` / `__NUXT__` / `__INITIAL_STATE__` 提 JSON | 毫秒级 | 服务端注入了状态 |
| **L3** | 浏览器 XHR | 浏览器打开页面，拦截它发出的请求 | 秒级 | 有运行时签名 |
| **L4** | DOM | 等渲染完，读 HTML 元素 | 秒级 + 易碎 | 只能看展示结果 |

**L0 是发现手段，不是数据层。** 找到接口后，仍要判断它属于 L1、L2 还是 L3。

**优先级：L0 → L1 → L2 → L3 → L4。**
越靠左越快、越省资源、越不容易被行为检测；越靠右越稳、越能拿登录态数据。

## 2. 签名剥离测试（核心 SOP）

### 2.1 为什么必须做

浏览器里 `fetch` 成功，可能是因为它自动带了：

- 登录 Cookie；
- 同源 `Origin` / `Referer`；
- 页面 JS 生成的签名参数（`a_bogus` / `msToken` / `w_rid` / `x-s` / `x-zse-96`）；
- 浏览器指纹 / TLS 会话；
- 页面运行时注入的临时 token。

把这些逐个剥离，才知道**最小必要集合**是什么。

### 2.2 五步流程

```text
① 在浏览器 Network 里找到目标请求
② 复制完整请求：URL / method / headers / cookies / body
③ 用 AntiRiskHttpClient 原样重放一次（基线）
④ 逐个剥离可疑项：签名参数 → 签名头 → 非必要头
⑤ 每次记录返回码，直到确定「最小必要集合」
```

**不要一次删光。** 一次只改一个变量，否则无法归因。

### 2.3 最小重放代码

```python
from anti_crawl_kit.http import AntiRiskHttpClient

client = AntiRiskHttpClient("demo", timeout=20, max_retries=1)

result = client.post_json(
    "https://目标站/graphql",
    json_data={
        "operationName": "visionProfile",
        "variables": {"userId": "目标ID"},
        "query": QUERY,
    },
    cookies={"登录cookie": "..."},
    headers={
        "Referer": "https://目标站/profile/123",
        "Origin": "https://目标站",
        "Accept": "application/json, text/plain, */*",
    },
)

print(result.status_code, result.risk.kind, result.risk.reason)
print(result.data if result.data is not None else result.text[:300])
```

> 手写 HTTP 必须用 `AntiRiskHttpClient`。裸 `requests` 的 TLS 指纹与 Chrome 不同，强风控站会直接 403，导致你误判「必须上浏览器」。

### 2.4 返回码 → 结论

| 现象 | 结论 | 下一步 |
|---|---|---|
| `200` + JSON + 目标字段 | **L1 可行** | 固化脚本，记录 `last_verified` |
| `200` + `result=1` / `status_code=0` + 数据 | **L1 可行** | 同上 |
| `200` + `result=2` / `need_login=true` | 缺登录态 | 补 Cookie，或走登录流程 |
| `200` + `result=21` / 参数校验错误 | 参数形态错 | 检查 ID 类型、字段名、必填参数 |
| `200` + `result=50` / 签名校验失败 | **L3** | 回浏览器拦截，或导出运行时签名再试 |
| `200` + 空 body | 可能是挑战页 / 需要运行时 | 看响应头、Cookie 是否被清；回 L3 |
| `200` + `_$jsvmprt` / JS 虚拟机壳 | 纯 HTTP 被反爬壳接管 | 必须浏览器运行时 |
| `400` + GraphQL `GRAPHQL_VALIDATION_FAILED` | 字段/层级写错 | 按报错改查询，不是签名问题 |
| `401` / `403` | 登录失效或风控 | 先补登录态；仍 403 再考虑 L3 |
| `429` | 限频 | 退避；不要重试轰炸 |
| `0` / 超时 / 连接失败 | 网络层 | 换网络或代理；不要归因成反爬 |

### 2.5 记录什么

每次探测至少落一条：

```json
{
  "platform": "demo",
  "access_path": "L1",
  "login_required": true,
  "signature_required": false,
  "minimal_headers": ["Cookie", "Referer", "Origin"],
  "field_semantics": {
    "followers": "ownerCount.fan",
    "works": "ownerCount.photo_public"
  },
  "last_verified": "2026-11-06",
  "evidence": "AntiRiskHttpClient 200, 229ms, 目标字段齐全"
}
```

## 3. 错误码字典：先读 JS，再猜

平台的 `result` / `status_code` 不是通用标准。**优先在 JS 里找错误码处理分支**，比盲试快得多。

### 3.1 通用模式

| 返回 | 常见含义 | 判断方法 |
|---|---|---|
| `status_code: 0` | 成功（抖音系常见） | 看是否有目标字段 |
| `result: 1` | 成功（快手系常见） | 看 `userProfile` 是否非空 |
| `result: 2` | 未登录 / 登录态失效 | 匿名请求常见 |
| `result: 21` | 参数格式错误 | ID 形态、字段名、必填参数 |
| `result: 50` | 签名校验失败 | 需要运行时签名 |
| `code: 0` / `errno: 0` | 成功（通用） | 结合 `data` 判断 |
| `code: -1` / `message` | 业务错误 | 读 message，不要当网络错误 |

### 3.2 从 JS 里找错误码

在页面加载的 **全部** JS 里搜：

```text
result === 21
result === 50
result == 2
sig4
verification
need_login
```

真实站点通常会把错误码和上报逻辑写在一起，例如：

```js
50 === t.data.result && sig4Report("sig4-verification-fail")
```

看到这行就能确定：`50` 是签名失败，不是「账号没作品」。

### 3.3 不要用「返回 200」判断成功

反爬常见做法是 **HTTP 200 + 业务错误码**，甚至 **HTTP 200 + 空 body**。
必须同时看：

- HTTP 状态码；
- 业务 `result` / `status_code` / `code`；
- 目标字段是否存在且类型正确；
- 响应长度是否异常（例如 226 字节空壳）。

## 4. ID 形态：同一个账号可能有 4 种 ID

| ID 形态 | 典型来源 | 用途 | 坑 |
|---|---|---|---|
| 数字 `userId` | 站内用户 ID | 部分 REST 接口 | 不一定被所有接口接受 |
| `eid` / 加密 ID | 资料接口返回 | GraphQL / 部分 REST | **不能拿数字 ID 代替** |
| `sec_uid` | 抖音主页 URL | Web 接口 | 和 `uid` 不通用 |
| `unique_id` / 短号 | 用户自定义 | 展示 / 搜索 | 可能为空或重复 |

### 规则

1. **用接口返回的 ID，不要自己转换。**
2. 一个接口失败时，先试「另一种 ID 形态」，而不是先怀疑签名。
3. 把「哪个接口要哪种 ID」写进平台适配器，不要散落在业务代码里。
4. 日志里记录实际使用的 ID 形态，排障时能省几小时。

### 真实踩坑

某平台 GraphQL 的 `userId` 参数：

- 传数字 ID → `result=21`、`userProfile=null`；
- 传 `eid` → `result=1`、数据完整。

**这不是签名问题，也不是账号没数据，是 ID 形态错了。**

## 5. 字段口径：`null` ≠ 0，同名 ≠ 同义

### 5.1 三个高频陷阱

| 陷阱 | 例子 | 正确做法 |
|---|---|---|
| `null` 当 0 | `photo: null`，实际公开作品是 `photo_public: 23` | 先确认字段语义，再决定缺失值 |
| 同名不同义 | `follower_count` vs `mplatform_followers_count` | 记录口径，不要混用 |
| 跨源不一致 | 移动 API 30/40/34，Web 36/45/43 | 选一个源做 canonical，另一个只做交叉校验 |

### 5.2 抖音实测：两个源的数字对不上

同一账号，同一时间窗口：

| 来源 | 粉丝 | 关注 | 作品 |
|---|---|---|---|
| 旧版移动 API | 30 | 40 | 34 |
| 登录态 Web 接口 | 36 | 45 | 43 |

差异不是 bug，而是**口径不同**（公开/多平台/缓存/统计范围）。
如果产品要展示「抖音粉丝数」，必须明确用哪个源，不能两个源混着用。

### 5.3 统一数据模型里必须带口径

```json
{
  "platform": "demo",
  "followers": 36,
  "following": 45,
  "works": 43,
  "field_semantics": {
    "followers": "web.profile.follower_count",
    "works": "web.profile.aweme_count"
  },
  "source": "L3_browser_xhr",
  "last_verified": "2026-11-06"
}
```

没有 `field_semantics` 的数字，三个月后没人知道它是什么。

## 6. L3 不是终点：拿到浏览器数据后还能再优化

很多团队做到 L3 就停了：能跑，但每次几秒、要维护浏览器生命周期。
L3 之后至少还有四级优化：

| 级别 | 做法 | 收益 | 风险 |
|---|---|---|---|
| **L3.1** | 持久化 `user-data-dir`，复用登录态 | 省登录，启动仍要 1s | profile 损坏 / 串号 |
| **L3.2** | 从浏览器导出 `msToken` / `a_bogus` 等运行时参数，用 `AntiRiskHttpClient` 重放 | 可能降到毫秒级 | 参数短时有效，需刷新 |
| **L3.3** | 用 `page.request` / CDP 在已开页面上下文直发请求 | 省页面渲染 | 仍依赖浏览器进程 |
| **L3.4** | 缓存 + 低频轮询 + 增量更新 | 降请求量 | 数据时效性下降 |

### 决策顺序

```text
L3 跑通
 ├─ 先问：签名参数是否短时有效？
 │   ├─ 是 → 导出参数，AntiRiskHttpClient 重放 → 成功则降到 L1
 │   └─ 否 → 保持 L3，优化 profile 复用和页面加载
 ├─ 再问：是否每次都要打开新页面？
 │   ├─ 是 → page.request / CDP 复用上下文
 │   └─ 否 → 保持
 └─ 最后：加缓存、降频、增量
```

**不要为了「纯 HTTP」去逆算法。** 逆出来的签名下周就可能过期；
优先让浏览器生成，再导出重放。

## 7. 登录态卫生

- Cookie / token 只放环境变量或密钥管理，**不要写进仓库、文档、日志**。
- 临时 Cookie 文件用完立即删除；浏览器 profile 按平台隔离。
- 日志里对 `Cookie` / `Authorization` / `token` 做脱敏。
- Cookie 出现在聊天记录、截图、issue 里，视为已泄露：退出登录或改密码。
- 批量任务用独立低权限账号，不要用主账号。
- 登录态失效要能识别（`401` / `result=2` / 跳登录页），不要静默返回空。

## 8. 验收清单

```text
[ ] 已确认接口属于 REST / GraphQL / HTML，不把 XHR 当数据源
[ ] 已在浏览器 Network 里拿到完整请求（URL / method / headers / body）
[ ] 已用 AntiRiskHttpClient 原样重放一次（基线）
[ ] 已逐个剥离签名参数/头，记录最小必要集合
[ ] 已确认 ID 形态（数字 ID / eid / sec_uid / unique_id）
[ ] 已确认字段口径（follower vs mplatform_followers，photo vs photo_public）
[ ] 已确认 null 不是 0，缺失值用 null 表示
[ ] 已记录 access_path / login_required / signature_required / last_verified
[ ] 已确认 200 不代表成功（业务错误码 / 空 body / 挑战页）
[ ] 已评估 L3 之后的优化（profile 复用 / 参数重放 / page.request）
[ ] Cookie 未入库、未入日志、临时文件已删除
```
