# 24 · 健康体检与静默失效

> 本文对应 `v0.3.0`。核心目标只有一个：**让「任务成功但数据为空」在 CI 里变成红色，而不是等用户投诉。**

---

## 1. 为什么静默失效最贵

真实事故（同一个项目里反复出现）：

| 现象 | 根因 | 发现方式 |
|---|---|---|
| 简书 / 掘金 / 百家号 2~4 秒「成功」完成，`item_cnt=0` | `runner.py` 的入口提取漏了三个平台分支 | 用户投诉 |
| CSDN 昵称 fallback 成 id | 主选择器 0 命中，兜底值被当成真值 | 人工核对 |
| 快手永远判「未登录」 | 认证 cookie 名单 Python / JS 两处漂移 | 用户投诉 |
| 主选择器 0 命中 | 靠兜底撑着，日志里没有告警 | 复盘发现 |
| `browser-data` 3.08 GB，登录窗卡十几秒 | `Cache / Code Cache / GrShaderCache` 无限增长 | 用户投诉 |

共同点：**程序没有抛异常**。所以「try/except 没报错」不能作为成功判据。

## 2. `RunReport` 强制四字段

`RunReport` 新增（缺一不可）：

| 字段 | 含义 | 缺失后果 |
|---|---|---|
| `expected_count` | 预期条目数（列表总数 / 已知应有条数） | 无法判断「拿到 3 条」是不是漏了 |
| `actual_count` | 实际有效条目数 | 无法区分「0 条」和「没跑」 |
| `degraded_reasons` | 降级原因（`dom_fallback` / `api_changed` / `partial_page`） | 降级被当成正常 |
| `source_strategy` | 实际数据源（`anonymous_json` / `ssr_state` / `xhr` / `dom`） | 出问题不知道走的哪条路 |

### 2.1 `actual_count=0` 一律是 `empty`

```python
report = RunReport.from_outcomes(
    "jianshu", "jianshu", outcomes,
    expected_count=20,
    actual_count=0,
    source_strategy="ssr_state",
)
assert report.status == "empty"      # 不是 ok
```

`status` 的判定顺序：

```
blocked  >  empty  >  degraded  >  ok
```

- `blocked`：`stop_reason` 命中 `captcha / blocked / rate_limited / signature_failed / risk / login_required`
- `empty`：`actual <= 0`（不管任务有没有抛异常）
- `degraded`：有降级原因，或条目覆盖率 < 100%
- `ok`：其余

### 2.2 `assert_thresholds` 增加覆盖率断言

```python
failures = assert_thresholds(
    report,
    min_success_rate=0.95,
    min_item_coverage=0.9,   # actual / expected
    allow_empty=False,       # 默认不允许 0 条
    allow_degraded=False,    # 默认不允许降级
)
```

`expected_count` 未知时不做条目覆盖率断言（返回 `None`），**不要伪造 1.0**。

## 3. `ack-health`：把改版变成例行检查

### 3.1 配置驱动

`ack-health` 不绑定任何框架，读 YAML / JSON：

```yaml
module_root: src
platforms:
  - platform: bilibili
    collector_module: mypkg.collectors.bilibili
    collector_class: BilibiliCollector
    login_module: mypkg.login
    cookie_module: mypkg.identity
    auth_cookies: [SESSDATA]
    entry_param: uid
    qrcode_selector: ".qrcode img"
    needs_login: true
    probe_url: https://space.bilibili.com/2
    probe_selectors: [".bili-video-card"]
    probe_state_names: ["window.__INITIAL_STATE__"]
```

```bash
ack-health --init                                  # 生成模板
ack-health --config ack_health.yaml                # 静态体检（秒级）
ack-health --config ack_health.yaml --browser      # + 免登录动态探针
ack-health --config ack_health.yaml --json out.json
```

### 3.2 静态检查（零浏览器）

| 维度 | 检查 | 失败含义 |
|---|---|---|
| A registry | 模块文件存在、类名逐字存在 | 注册表指向了不存在的实现 |
| B entry | `entry_param` 在采集器源码出现 | 入口提取漏分支（简书/掘金/百家号事故） |
| C login | 认证 cookie 名单在源码出现、二维码选择器存在 | 名单漂移 / 登录判定永远失败 |
| D probe_drift | 探针选择器仍在源码中 | 探针清单过期，体检结论不可信 |
| E probe | 打开 `probe_url`，选择器/状态对象命中数 | 0 命中 = 疑似改版 |

四档状态 `OK / WARN / FAIL / SKIP`，`FAIL > 0` 退出码 1，可直接接 CI。

### 3.3 红线

- 只读探测：不点击、不登录、不发布、不写平台数据。
- `stdout` 面向 Windows GBK 终端：只用 `[OK]/[WARN]/[FAIL]/[SKIP]`，不用 emoji。
- 未配置 `probe_url` 的平台标 `SKIP`，**不硬编易失效的账号 ID**。

## 4. profile 缓存治理

```python
from anti_crawl_kit import prune_profile_cache

result = prune_profile_cache("profiles/douyin")
print(result.reason, result.freed_mb)
```

### 4.1 白名单（只删这些）

```
Default/Cache, Default/Code Cache, Default/GPUCache,
Default/DawnGraphiteCache, Default/DawnWebGPUCache,
Default/GrShaderCache, Default/ShaderCache,
Default/blob_storage, Default/CacheStorage,
Default/Service Worker/CacheStorage, Default/Service Worker/ScriptCache,
Default/Media Cache, Default/Application Cache,
ShaderCache, GrShaderCache, GPUCache, GraphiteDawnCache,
Crashpad, BrowserMetrics, component_crx_cache, extensions_crx_cache
```

### 4.2 绝对不碰

```
Default/Network/Cookies, Default/Local Storage, Default/IndexedDB,
Default/Preferences, Default/Login Data, Default/Web Data, Local State
```

### 4.3 双阈值 + 24h 节流

- 缓存 > `max_cache_mb`（200MB）**或** profile 总体 > `max_total_mb`（400MB）才动手；
- 24h 内不重复清理；但缓存再次翻倍时强制清理；
- 任何异常全部吞掉，返回 `freed_mb=0`，绝不阻塞主流程；
- `dry_run=True` 只计算不删除。

实战效果：**3162 MB → 142 MB，登录态完好**。

## 5. 首导航自愈 + 慢加载语义

### 5.1 首导航自愈

`PageAdapter.goto` 内置 `_ensure_initial_navigation_ready(retries=2, timeout=7)`：

- 轮询 `document.readyState` 到 `interactive / complete`；
- `about:blank` 跳过；
- `chrome-error://` 视为可交互；
- **坑**：patchright 1.62.1 的 sync `Page.evaluate` **没有** `timeout` 参数，别照 1.61.2 写。

### 5.2 慢加载 ≠ 失败

五轮对照实验证明技术栈没有性能缺陷，慢是**平台时段性惩罚窗口**：
passport challenge 挂起 9~13s，同代码跨时段差 3~6 倍。

`goto` 超时后：

1. 先检查页面是否已经可交互；
2. 可交互 → 记 `slow_load=True`，继续，不关窗；
3. 仍不可交互 → 抛 `TimeoutError`，文案带「等待 1~2 分钟再试，不要反复重开」。

指标写入 `page.last_nav_metrics`：

```python
{
    "url": "...",
    "attempts": 1,
    "goto_ms": 12345,
    "ready_state": "interactive",
    "slow_load": True,
    "recovered_from_timeout": False,
    "error": "",
}
```

**诊断与 bench 不要截图**：项目实测 `screenshot()` 会把 10~12s 拉到 25~40s，
测出来的数据是假的。读指标即可。

环境变量 `AC_KIT_SLOW_LOAD_MS` 可覆盖慢加载阈值（默认 15000）。

## 6. 固定失败归因优先级

```python
from anti_crawl_kit import WaitReason, classify_wait_outcome

reason = classify_wait_outcome(outcome, item_count=0, browser_closed=False)
```

优先级（从高到低）：

```
浏览器关闭 > 人机验证未完成 > 未登录 > 过验证码后仍空 > 一般空结果
```

对应 `WaitReason`：

```
browser_closed / captcha_not_done / not_logged_in /
empty_after_captcha / empty_result / ok
```

`WaitOutcome.reason` 由 `wait_for_captcha_and_login` 直接填好，不要再自己拼归因。
抖音曾把「未登录 / 关窗」统一误报成「验证码已等待完成但被风控」，排查方向直接被带偏。

## 7. GBK 控制台兜底 + 脱敏

```python
from anti_crawl_kit import install_safe_print, redact_secrets

install_safe_print()          # 进程级兜底，幂等
print("标题", title)          # 不会再因为 \xa0 / emoji 炸掉主流程

safe = redact_secrets(raw_log)  # 上报/落盘前脱敏
```

- `safe_print`：`UnicodeEncodeError` 时逐参数降级重试；
- `redact_secrets`：遮 cookie / token / password / signature，保留 key；
- `redact_mapping`：递归脱敏 dict / list。

真实事故：快手标题含 `\xa0` → `UnicodeEncodeError` → 外层 `except` 把**已经拿到的直链结果**整体吞掉。

## 8. 平台注册表单一来源

```python
from anti_crawl_kit import (
    PlatformCapability, PlatformSpecRegistry,
    derived_view, validate_spec, check_derived_consistency,
)

spec = PlatformCapability(
    platform="kuaishou",
    auth_cookies=("kuaishou.web.cp.api_ph", "kuaishou.web.cp.api_st"),
    collector_module="mypkg.collectors.kuaishou",
    collector_class="KuaishouCollector",
    entry_param="user_id",
)

registry = PlatformSpecRegistry([spec])
assert registry.validate() == []
registry.assert_consistent({
    "kuaishou": {
        "auth_cookies": {
            "python": ["kuaishou.web.cp.api_ph", "kuaishou.web.cp.api_st"],
            "javascript": ["kuaishou.web.cp.api_ph", "kuaishou.web.cp.api_st"],
        },
        "entry_param": ["user_id"],
    }
})
```

- `derived_view(spec)`：所有派生点的规范视图；
- `check_derived_consistency(spec, derived)`：比对派生点（列表不区分顺序）；
- `PlatformSpecRegistry.fingerprint()`：稳定指纹，用于快照测试；
- 重复注册直接抛 `ValueError`。

真实事故：新增 3 个平台时能力表、采集器、发布器都加了，唯独 `runner.py`
入口提取漏分支 → 全空；同一次事故里还有 cookie 名单 Python/JS 漂移（快手）、
桌面端 JS 登录窗裸 patchright 无 stealth。

## 9. 发行门槛：真实站点冒烟（`ack-smoke`）

`v0.4.0` 已落地 `ack-smoke`：9 条真实站点用例 / 8 种类型，默认全部是公开练习站
（允许抓），输出 JSON + 退出码，`FAIL > 0` 返回 1。

覆盖：

1. 纯 HTTP 静态 / 分页（books.toscrape.com、web-scraping.dev）；
2. JS 渲染空壳（HTTP 0 条 → 浏览器 10 条）；
3. 大列表覆盖率（250 / 250）；
4. 慢加载（延迟 10s 仍拿到 10 条）；
5. 无限滚动 + 停止条件；
6. 登录链路（公开测试账号）；
7. **负向控制**：故意写错选择器，必须判 FAIL。

```bash
ack-smoke --json smoke.json          # 发版前必跑
ack-smoke --no-browser --strict      # CI 里可强制要求浏览器用例
```

**mock 不算验证**：patchright 大切换那次只跑了 mock + 检测站 + 百度，
各平台真实 DOM/接口链路没实测，复盘时被列为最大风险项。

详见 [`docs/25-真实站点冒烟.md`](25-真实站点冒烟.md)。

## 10. 验收清单

- [ ] `RunReport` 带 `expected_count / actual_count / degraded_reasons / source_strategy`
- [ ] `actual_count=0` 时 `status == "empty"`，CI 断言失败
- [ ] `ack-health --config ...` 静态体检通过；故意改错类名 → 退出码 1
- [ ] `prune_profile_cache` 后 `Default/Network/Cookies` 仍存在
- [ ] `goto` 超时但 `readyState=complete` 时不抛异常，`slow_load=True`
- [ ] `WaitOutcome.reason` 按固定优先级归因
- [ ] `install_safe_print()` 后 GBK 终端不再炸
- [ ] `PlatformSpecRegistry.assert_consistent(...)` 在派生点漂移时抛异常
- [ ] 诊断/bench 不调用 `screenshot()`
