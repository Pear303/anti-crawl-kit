# 01 · 决策与方法论

## 1. 先选数据源，再写代码

同一个页面通常有四条取数路径。选错路径的代价不是「慢一点」，而是「写完发现
数据不全 / 一改版就崩 / 天天被风控」。

| 层级 | 数据源 | 成本 | 稳定性 | 适用 |
|---|---|---|---|---|
| L0 | JS 包静态分析（找接口） | ★ | ★★★ | HTML 空壳、数据由前端 JS 拉取 |
| L1 | 公开 HTTP JSON 接口 | ★ | ★★★ | 榜单、搜索、详情（无签名） |
| L2 | 页面 SSR 全局状态 | ★★ | ★★★ | `__INITIAL_STATE__` / `__NEXT_DATA__` / `window.__NUXT__` |
| L3 | 页面 XHR 响应拦截 | ★★ | ★★☆ | 登录态接口、滚动加载 |
| L4 | DOM 解析 | ★★★ | ★☆ | 无接口、强 SSR、结构简单 |

**判断顺序：**

1. 先 `requests` 抓一次 HTML，搜目标数字/字段。**HTML 里有 → 直接 L2/L4，不要上浏览器。**
2. HTML 是空壳（数字是空的 `<p>`、只有一个 `<script src>`）→ 跑 `tools/js_api_hunt.py`，
   在 JS 包里搜 `baseURL` / `.get("/xxx")` / 字段名，拼出真实接口（L0）。
3. 找到接口 → 先用 HTTP 直连试（curl_cffi）。能过就用 L1。
4. 直连 403 / 需要签名 → 浏览器打开，`page.capture_responses()` 拦截（L3）。
5. 页面源码里搜 `__INITIAL_STATE__`、`__NEXT_DATA__`、`__NUXT__` → L2。
6. 都没有 → L4，并且优先用「声明式配置」而不是硬编码。

> **最容易犯的错：** 一看 HTML 没数据就开浏览器。先花 10 分钟查 JS 包，
> 很多时候接口就明明白白写在里面（见 `09-JS包找接口.md`）。

> 实战经验：内容平台的列表页 80% 有 XHR JSON；详情页 50% 有 SSR 状态；
> 只有评论、弹幕、部分创作者主页必须解析 DOM。

### 1.1 `api_discovery` vs `js_bundle`：别用错

这两个都能「找接口」，但前提和成本完全不同：

| | `api_discovery`（浏览器内） | `js_bundle`（零浏览器） |
|---|---|---|
| 前提 | 浏览器已打开，页面能正常渲染 | 只需要 HTML + JS 文件 |
| 看什么 | 页面**实际发出**的 XHR | JS 包里**写死**的接口 |
| 适合 | 动态 import、混淆、接口在运行时生成 | HTML 空壳、静态 JS、接口地址明文 |
| 成本 | 秒级 ~ 十秒级 | 毫秒级 |
| 入口 | `examples/06_api_discovery.py` | `tools/js_api_hunt.py` |

**判断顺序：先 `js_bundle`（快、零浏览器），找不到再开浏览器用 `api_discovery`。**

反过来的代价：为了看一个接口，先花 10 秒启动浏览器、等页面渲染、再抓 Performance，
而其实 JS 包里第一行就写着 `baseURL`。

> 选型决策（API vs HTML、五维打分、双跑校验、回滚开关）见
> [`19-数据源选型与兜底.md`](19-数据源选型与兜底.md)。

## 2. 反爬的三层模型

不要把所有问题都归因于「指纹」。风控通常分三层，成本和触发顺序不同：

### 2.1 环境层（你是谁）

- TLS 指纹（JA3/JA4）、HTTP/2 指纹
- User-Agent、`sec-ch-ua`、Accept-Language、时区
- `navigator.webdriver`、CDP 泄漏、命令行参数
- Canvas / WebGL / Audio / 字体指纹
- IP 归属、代理质量、ASN

**对策：**
- 浏览器：patchright（驱动层修复）+ 真实系统 Chrome + 不伪造 UA。
- HTTP：`curl_cffi` 的 `impersonate="chrome120"`。
- 代理：住宅/移动 > 机房；同一账号固定出口 IP。

### 2.2 行为层（你像不像人）

- 固定间隔的请求、固定滚动距离、瞬间填表
- 无鼠标轨迹、无焦点变化、无停顿
- 单位时间请求数、页面停留时长、点击热区

**对策：**
- 随机延时 + 抖动（`behavior.py`）
- 贝塞尔鼠标轨迹、变速键入、概率回滚
- 同域导航限频（`guard.py`）
- 不要追求「完全拟人」——CDP 合成输入始终有 `isTrusted` 等破绽，
  行为模拟的目标是**降低机械节奏特征**，不是骗过行为级检测。

### 2.3 协议层（你带了什么凭证）

- Cookie / token / 签名参数（`a_bogus`、`w_rid`、`X-s`、`xsec_token`）
- Referer / Origin
- 请求顺序（必须先访问页面拿 cookie，再调接口）
- 频控与配额

**对策：**
- 优先复用真实浏览器会话（持久化 profile）。
- 签名参数从页面 JS/SDK 取，不要硬编码。
- 需要签名的接口，用浏览器执行页面函数生成，或 Node 跑签名脚本。

> 排障顺序：先确认是**哪一层**触发。403 + 「请登录」是协议层；
> 200 但内容为空、验证码页是行为/环境层；直接 429 是频控。
> 层次判断错，后面所有优化都是白费。

## 3. 采集器架构：配置驱动优先

一个平台采集器最小由五部分组成：

```
PlatformSpec
├─ 入口 URL
├─ 登录检测（可选）
├─ 验证码检测（可选）
├─ 列表/卡片选择器 + 字段映射
└─ 滚动/翻页策略
```

能用配置表达就用 `GenericCollector`；只有以下情况才写自定义代码：

- 需要拦截 XHR / 调签名接口
- 需要多级详情页（列表 → 详情 → 评论）
- 需要复杂交互（切 tab、展开、下拉加载）
- 需要视频/音频直链解析与下载

**判断标准：** 如果新平台接入需要改 3 个以上文件，说明抽象层没做好。

## 4. 数据质量四件事

采集跑通不等于数据可用。上线前必须处理：

### 4.1 去重

优先级：`platform:id` > `platform:规范化URL` > `platform:keyword:author:title`。

URL 规范化要：去 query、去 fragment、去末尾 `/`。
（`text.make_dedupe_key` 已实现。）

### 4.2 计数归一

`1.2万` → `12000`，`1,093` → `1093`，`-` / 空 → `None`。
注意 DOM 里常有零宽字符（`\u200b`），先剥离再解析。

### 4.3 文本清洗

- 剥离 `<em class="keyword">` 高亮标签
- HTML 实体还原
- 反爬水印：连续 `word`、`mmMwWLliI0fiflO` token、零宽字符

### 4.4 完整性

每条记录至少要有：平台、唯一 ID、URL、标题、作者、采集时间。
指标字段允许缺失，但要用 `None` 而不是 `0` 区分「没有」和「真的是 0」。

## 5. 工程约束（上线前检查）

- **幂等**：同一任务重复执行不会产生重复数据。
- **可中断**：长循环内部检查取消信号（滚动、翻页、等待登录都要）。
- **可恢复**：断点信息（页码/游标/已采 ID）持久化。
- **可观测**：每个阶段有日志（导航、登录、验证码、提取条数、风控命中）。
- **限频**：默认保守；宁可慢，不要封号。
- **降级**：接口失败 → 浏览器；DOM 失败 → 接口；主选择器失败 → 兜底选择器。
- **资源回收**：浏览器、driver 子进程、临时文件、下载 `.part` 必须能清理。

## 6. 成本模型（决定要不要上浏览器）

粗略量级（单机）：

| 方式 | 单条耗时 | 内存 | 适合规模 |
|---|---|---|---|
| HTTP 直连 | 50-300ms | < 50MB | 万级/天 |
| 浏览器 + 接口拦截 | 1-3s | 300-800MB | 千级/天 |
| 浏览器 + DOM | 3-10s | 300-800MB | 百级/天 |
| 浏览器 + 详情页逐条 | 5-15s/条 | 300-800MB | 十级/天 |

如果预算允许，**混合架构**最优：
浏览器只负责「拿 cookie / 拿签名 / 打开一次页面」，
批量数据用页面上下文里的 `fetch` 或 HTTP 直连完成。

`PageAdapter.api_request()` 就是这条路：请求走浏览器上下文，自动带 cookie，
但不渲染页面，成本接近 HTTP。
