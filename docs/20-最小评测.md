# 最小评测：curl_cffi vs patchright

> 目的不是「证明浏览器更强」，而是用数据回答一个具体问题：
> **这个站，HTTP 直连够不够？不够再上浏览器。**

---

## 1. 为什么需要评测

工作包里有一堆「优先 HTTP、失败再降级」的规则，但规则不能代替实测：

- 同样是 200，有的站 HTML 里就有数据，有的站只有空壳；
- 同样是浏览器，有的站 `domcontentloaded` 就够，有的站要等 XHR；
- 同样是「慢」，有的是网络慢，有的是渲染慢，有的是被限速。

不评测就会出现两种浪费：

1. 明明 HTTP 能拿，却默认开浏览器，成本翻倍；
2. 明明 HTTP 被拦，却反复重试，把风控评分越刷越高。

---

## 2. 怎么跑

```bash
# 默认 3 站 × 2 工具 × 1 次
python tools/bench.py

# 取中位数（推荐，单次受网络波动影响）
python tools/bench.py --repeat 3

# 只跑 HTTP（不开浏览器）
python tools/bench.py --only http

# 有头浏览器（观察真实页面）
python tools/bench.py --headed

# 指定输出目录
python tools/bench.py --out benchmarks/2026-11
```

输出：

```text
<out>/
├─ report.md      # 人看的表格 + 结论
└─ results.json   # 机器读的原始数据
```

### 指标

| 指标 | 含义 |
|---|---|
| `ok` | 状态 200 + HTML 超过阈值 + 无验证码 |
| `status` | HTTP 状态码 |
| `elapsed_ms` | 单站耗时（不含浏览器启动） |
| `bytes` | 响应/页面大小 |
| `items` | 用站点选择器数出的卡片数（验证数据是否真在） |
| `risk` / `detection` | 风险分类 + WAF 指纹 |

`items` 是关键：**200 不代表有数据**。空壳页也会返回 200。

## 3. 默认三站

| 站点 | URL | 选择器 | 类型 |
|---|---|---|---|
| quotes | `quotes.toscrape.com` | `div.quote` | 静态练习站 |
| books | `books.toscrape.com` | `article.product_pod` | 静态练习站 |
| biquge | `www.biquge.mom` | `.book-card` | 中文小说站（SSR） |

选这三站的原因：

- 两站结构稳定，适合做基线；
- 一站是真实中文站，验证「非英文站 + 真实 CDN」；
- 都不需要登录，评测可重复。

---

## 4. 实测结果（2026-11-05，`--repeat 3`）

环境：Windows 11 · Python 3.13.3 · curl_cffi 0.15.0 · 系统 Chrome。
浏览器启动耗时：**1071 ms**（不计入单站耗时）。

| 站点 | 工具 | 成功 | 状态 | 耗时(ms) | 大小(KB) | 卡片数 |
|---|---|---|---|---|---|---|
| quotes | http | ✅ | 200 | 920 | 10.8 | 10 |
| quotes | browser | ✅ | 200 | 623 | 10.7 | 10 |
| books | http | ✅ | 200 | 1200 | 50.1 | 20 |
| books | browser | ✅ | 200 | 1359 | 49.8 | 20 |
| biquge | http | ✅ | 200 | 483 | 26.9 | 24 |
| biquge | browser | ✅ | 200 | 831 | 27.5 | 24 |

### 结论

1. **三站都是 SSR，HTTP 全部够用。** 卡片数与浏览器完全一致（10 / 20 / 24），说明数据确实在 HTML 里，不是渲染出来的。
2. **单页耗时接近，浏览器甚至可能更快。** 本地系统 Chrome + `domcontentloaded`，导航时间主要受网络影响，渲染开销没有想象中大。
3. **但浏览器有固定启动成本。** 每次任务约 1 秒；批量 100 页时，这 1 秒会被摊薄，但「每页一个浏览器上下文」的开销会放大。
4. **HTTP 的真正优势是并发和资源。** 不用渲染、不用 GPU、不用维护 profile，可以开几十个并发；浏览器通常只能开个位数。

**所以默认策略不变：能 HTTP 就 HTTP；只有 HTTP 被拦、或数据必须靠 JS 渲染时才上浏览器。**

## 5. 评测暴露的两个真实缺陷

这轮 benchmark 顺带修了 `risk.py` 的两个误判。它们比「跑分」更有价值。

### 5.1 正常登录文案被误判成验证码墙

知乎首页 HTTP 200、45 KB，但被 `classify_http_result` 判成 `captcha`。
原因：全文包含「验证码」，命中了 `"验证码" in text`。

实际那是首页登录弹窗里的「验证码登录」「获取短信验证码」，不是验证码墙。

**修复：**

- 去掉裸「验证码」；
- 改用更具体的「请输入验证码」「滑动验证」「拖动滑块」「请完成验证」；
- 验证码判断只看可见文本和 `<title>`，不看 `<script>`。

### 5.2 200 + 短 JSON 登录墙被漏判

微博未登录返回：

```json
{"ok":-100,"url":"https://weibo.com/login.php"}
```

状态 200、47 字节。旧逻辑只看状态码，判成 `ok`。

**修复：** 短 JSON（< 800 字节）里出现 `"ok":-100`、`"code":-1`、`login.php` 等标记时，判 `login_required`。

### 5.3 修复后的分类

| 站点 | 修复前 | 修复后 | 实际情况 |
|---|---|---|---|
| 知乎 | `captcha` ❌ | `login_required` | SPA 壳 + 登录弹窗，降级浏览器合理 |
| 微博 | `ok` ❌ | `login_required` ✅ | 短 JSON 登录墙 |
| 豆瓣 | `ok` ✅ | `ok` | 正常 SSR |
| 小红书 | `captcha` ✅ | `captcha` | 真的重定向到 `/website-login/captcha` |

## 6. 局限

| 局限 | 说明 |
|---|---|
| 站点太少 | 3 站只能做基线，不能覆盖强风控站（Cloudflare / DataDome） |
| 单次波动 | 网络抖动会影响耗时，务必 `--repeat 3` |
| 本地 Chrome 偏快 | 生产服务器/容器里浏览器启动通常更慢 |
| 未计代理成本 | 生产环境常挂代理，HTTP 和浏览器都受影响 |
| `items` 依赖选择器 | 选择器写错会误判「没数据」 |

---

## 7. 怎么加站点

改 `tools/bench.py` 的 `DEFAULT_SITES`：

```python
Site("zhihu", "https://www.zhihu.com/", "section.feed-item"),
Site("xhs", "https://www.xiaohongshu.com/", "section.note-item"),
```

或者临时用环境变量/命令行（当前版本需要改代码，保持简单）。

加站点时注意：

1. **不要加需要登录的站**，否则评测变成「登录态测试」；
2. **不要高频请求**，每站 3 次已经够；
3. **选择器要能数出卡片**，否则 `items=0` 无法判断是「没数据」还是「选择器错」。

---

## 8. 一句话

> **先跑 benchmark，再决定要不要开浏览器。**
> 跑分不是为了选一个「最强工具」，而是为了知道每个站的**最低成本路径**。
