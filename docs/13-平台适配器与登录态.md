# 13 · 平台适配器与登录态

> 接一个新平台，真正花时间的不是写采集逻辑，而是回答这些问题：
> **要不要登录？登录怎么判断？二维码在哪？哪些字段平台根本不给？频率多少？**
>
> 本文给出一张「平台描述表」和一套「登录态三态校验」，照着填就行。

---

## 1. 一个平台需要描述什么

不要把这些信息散落在 5 个文件里。用一个 dataclass 收敛：

```python
@dataclass(frozen=True)
class PlatformCapability:
    platform: str                 # 标准标识 "demo"
    label: str                    # 中文名 "示例平台"

    # ── 登录 ──
    creator_center_url: str = ""  # 创作者中心 / 后台入口
    supports_login: bool = False
    auth_cookies: list[str] = field(default_factory=list)   # 认证 cookie 名
    cookie_domain: str = ""       # 用于 SQLite 匹配，如 "example.com"
    handle_source: dict = field(default_factory=dict)       # 身份比对来源
    qrcode_selector: str = ""     # 二维码定位
    qrcode_selector_type: str = "role"   # "role" | "css" | "iframe_role"

    # ── 采集 ──
    collector_module: str = ""
    collector_class: str = ""
    entry_param: str = ""         # 入口参数名：uid / user_id / sec_uid / url
    needs_login: bool = False
    known_unavailable: dict = field(default_factory=dict)   # 平台不提供的字段

    # ── 发布 ──
    publisher_module: str = ""
    publisher_class: str = ""
    supports_text_publish: bool = False
    publish_url: str = ""
    supports_video_publish: bool = False
    video_publish_url: str = ""

    # ── 频率 ──
    rate_limit: dict = field(default_factory=dict)
```

### 字段解释

| 字段 | 为什么重要 | 示例 |
|---|---|---|
| `auth_cookies` | 判断「是否登录」的唯一可靠依据 | `["SESSDATA"]` |
| `cookie_domain` | 直读 Chromium SQLite 时匹配 `host_key` | `"bilibili.com"` |
| `handle_source` | 防止 profile 被污染后采错账号 | `{"type":"json","url":"...","json_path":"data.mid"}` |
| `qrcode_selector_type` | 二维码可能在 iframe 里 | `"role"` / `"css"` / `"iframe_role"` |
| `entry_param` | 采集器入口参数名不统一 | `uid` / `sec_uid` / `user_id` |
| `known_unavailable` | 避免反复排查「平台根本不给」的字段 | `{"play_count":"网页端不提供"}` |
| `rate_limit` | 不同平台风控强度差异大 | `{"min_interval":3,"max_per_hour":200}` |

## 2. 平台注册表：一个文件管所有平台

```python
PLATFORM_REGISTRY: dict[str, PlatformCapability] = {
    "demo": PlatformCapability(
        platform="demo",
        label="示例平台",
        creator_center_url="https://creator.example.com/",
        supports_login=True,
        auth_cookies=["sessionid"],
        cookie_domain="example.com",
        handle_source={"type": "json", "url": "https://api.example.com/me",
                       "json_path": "data.uid"},
        qrcode_selector='img[name="二维码"]',
        qrcode_selector_type="role",
        collector_module="collectors.demo.works",
        collector_class="DemoWorksCollector",
        entry_param="uid",
        needs_login=True,
        known_unavailable={"play_count": "网页端不提供"},
        rate_limit={"min_interval": 3, "max_per_hour": 200},
    ),
}
```

### 三条规则

1. **新增平台只改这一个文件。** 登录、采集、发布、监控都从这里读。
2. **cookie 名单必须与登录侧同源。** 如果登录配置在 JS/另一个模块里，两边要互相注释「修改需同步」。
3. **`known_unavailable` 要写原因。** 否则半年后又会有人去查「为什么播放量是空的」。

## 3. 登录态三态校验

不要用 `bool` 表示登录态。至少三态：

```text
valid    → 有未过期的认证 cookie，且身份可确认
expired  → 有认证 cookie，但已过期
missing  → 没有认证 cookie（从未登录）
```

### 3.1 为什么不能只看「cookie 存在」

- Chromium 加载持久化存储时，会**清理内存里的过期 cookie**；
- 过期 cookie 在 Playwright 里表现为「缺失」；
- 只看存在性，会把「登录过期」误判成「从未登录」。

### 3.2 正确做法：直读 Cookies SQLite

Chromium 的 cookie 存在 `profile/Default/Cookies`（SQLite），字段 `expires_utc` 是 **WebKit 纪元**（1601-01-01）。

```python
CHROME_EPOCH_OFFSET = 11_644_473_600   # 1601 → 1970 的秒差

def cookie_expired(expires_utc: int) -> bool:
    if not expires_utc:
        return False                    # 0 = 会话 cookie，不过期
    unix_ts = expires_utc / 1_000_000 - CHROME_EPOCH_OFFSET
    return unix_ts < time.time()
```

判定逻辑：

```python
def eval_cookie_state(cookies, auth_names):
    matched = [c for c in cookies if c["name"] in auth_names and c["value"]]
    if not matched:
        return "missing"
    if all(cookie_expired(c["expires_utc"]) for c in matched):
        return "expired"
    return "valid"
```

### 3.3 降级策略

直读 SQLite 失败（文件锁、格式变化、权限）时：

```text
SQLite 直读失败 → 回退 Playwright cookies 的 expires 字段
                 → 再失败 → 只做存在性校验
```

**任何校验异常都不要阻塞任务**，降级为「尽力而为」，并在日志里标注 `degraded`。

## 4. 身份比对：防止 profile 被污染

「登录了」不等于「登录的是你要的账号」。

### 4.1 什么时候必须比对

| 场景 | 是否比对 | 原因 |
|---|---|---|
| 采集公开数据 | 可选 | 用错账号最多数据不准 |
| 采集「我的作品」 | **必须** | 用错账号会采到别人的数据 |
| 发布内容 | **必须** | 发错账号是事故 |
| 账号矩阵监控 | **必须** | 指标会串 |

### 4.2 身份来源

| 类型 | 做法 | 示例 |
|---|---|---|
| `json` | 带 cookie 请求接口，按 JSON path 取 handle | B站 `/x/member/web/account` → `data.mid` |
| `cookie` | handle 就是某个 cookie 的值 | CSDN `UserName` |
| `dom` | 页面上的用户 ID/昵称 | 没有稳定接口时 |

```python
HANDLE_SOURCES = {
    "demo": {
        "type": "json",
        "url": "https://api.example.com/me",
        "json_path": "data.uid",
    },
}
```

### 4.3 结果处理

```text
valid + handle 一致     → 通过
valid + handle 不一致   → 失败，提示「请为账号 XX 重新登录」
expired / missing       → 采集任务放行（现场等登录）；发布任务失败
```

**关键决策：未登录放行、身份不符阻断。**

- 未登录：采集器可以现场等用户登录，不应该在预检阶段就拦住；
- 身份不符：属于客观不可用，继续跑只会污染数据，必须失败。

### 4.4 handle 规范化

平台返回的 handle 格式可能不一致：

```text
账号表存 "mid:12345"，接口返回 "12345"
账号表存 "uid:abc"，接口返回 "abc"
```

比对前剥掉 `mid:` / `uid:` / `douyin_id:` 等前缀：

```python
def normalize_handle(raw: str) -> str:
    return re.sub(r"^(mid|uid|douyin_id|sec_uid):", "", raw.strip())
```

## 5. 二维码登录的三种定位方式

| 类型 | 适用 | 写法 |
|---|---|---|
| `role` | 有 `img[name="二维码"]` 之类语义 | `img[name="二维码"]` |
| `css` | 平台用哈希 class | `img.css-wemwzq` |
| `iframe_role` | 二维码在 iframe 里 | 先 `frame_locator`，再定位 |

**坑：**

- 哈希 class 会随构建变化，优先用 `role` / `name` / `alt`；
- iframe 里的二维码，`page.locator` 找不到，必须 `page.frame_locator(...)`；
- 二维码是图片，登录阶段**不要拦截图片**。

## 6. 字段可用性表

有些字段平台根本不给，写进 `known_unavailable`，避免反复排查：

```python
known_unavailable = {
    "play_count": "网页端不提供单条播放量",
    "total_views": "创作者中心不提供总播放量",
    "resolution": "旧视频缺少 ratio 字段",
}
```

排查字段为空时，先查这张表：

```text
字段为空
├─ known_unavailable 里有 → 平台限制，跳过
├─ 接口返回有、解析后没有 → 解析 bug
├─ 接口返回就没有 → 权限/登录/字段改名
└─ 接口没请求 → 选择器/参数错
```

## 7. 频率限制：按平台分档

```python
rate_limit = {
    "min_interval": 3,        # 两次请求最小间隔（秒）
    "max_per_hour": 200,      # 每小时上限
    "backoff_on_429": 60,     # 429 后冷却（秒）
}
```

| 平台档位 | 典型平台 | 建议 |
|---|---|---|
| 宽松 | 公开榜单、RSS | 1~2s |
| 中等 | 大部分内容平台 | 2~4s |
| 严格 | 强风控平台 | 5~10s + 随机抖动 |
| 极严 | 需要签名/登录的接口 | 10~30s，串行 |

**不要所有平台用同一个值。** 宽松平台被限速是浪费，严格平台用宽松值会封号。

## 8. 新增平台 checklist

```text
[ ] platform / label 确定
[ ] 入口 URL（创作者中心 / 列表页 / 详情页）
[ ] auth_cookies（实测确认，不要抄旧文档）
[ ] cookie_domain（SQLite host_key 匹配用）
[ ] handle_source（能比对就填，不能就留空并注明）
[ ] qrcode_selector + type（实测能定位）
[ ] collector_module / class
[ ] entry_param（uid / sec_uid / user_id / url）
[ ] needs_login
[ ] known_unavailable（已知平台限制）
[ ] rate_limit（按风控强度选档）
[ ] publisher（如果支持发布）
[ ] 一条平台速查记录（docs/07）
[ ] 登录态三态实测：valid / expired / missing 各一次
[ ] 身份比对实测：正确账号通过、错误账号阻断
```

## 9. 登录态排障速查

| 症状 | 可能原因 | 动作 |
|---|---|---|
| 显示「未登录」但页面是登录的 | auth cookie 名单过时 | 复制 profile → 有头登录 → dump cookie 名 |
| 显示「已登录」但采集 401 | cookie 过期 / 域名不对 | 直读 SQLite 看 `expires_utc` |
| 登录成功但判定失败 | cookie 是 HttpOnly / 跨域 | 用 `context.cookies()` 而不是 `document.cookie` |
| 同一账号一会有效一会无效 | 多 profile 并发 / 锁冲突 | 检查是否有多个进程用同一 profile |
| 身份比对总是不一致 | handle 格式差异 | 比对前 `normalize_handle` |
| 发布用错账号 | 没做身份比对 | 发布前强制 `handle` 校验 |

**最有效的一招：** 复制一份 profile → 用有头浏览器登录 → dump 所有 cookie 的 `name/domain/expires`。比猜快 10 倍。
