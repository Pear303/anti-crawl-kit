# 19 · 数据源选型与兜底

> 回答一个问题：**同一个页面有 API 和 HTML 两条路，生产该选哪条？**
>
> 结论不是「API 更好」或「HTML 更稳」，而是：
> **先按五个维度打分，再从四种策略里选一种，最后用双跑校验兜住静默失效。**

---

## 0. 一句话

> **私有 API 的价值是「多一条快路径」，不是「可以扔掉 HTML」。**
> 没有失效监控和回退开关的 API 主路径，等于「平时快、出事停」。

---

## 1. 先分清三种局面

不要一上来就讨论「API vs HTML」，先看有没有得选。

| 局面 | 判断 | 结论 |
|---|---|---|
| **A. HTML 无数据** | 页面是空壳，数据由 JS 拉取 | API 是**唯一路径**，不存在选型 |
| **B. API + HTML 都能用** | HTML 有数据，接口也能调 | **才有选型问题**，按第 2 节打分 |
| **C. 只有 HTML** | 没有可用接口 | HTML 是唯一路径，重点是选择器兜底 |

**只有局面 B 需要做「权衡」。** 局面 A 要做的是「监控 + 兜底」，不是「比较」。

---

## 2. 五维打分

给每条候选路径打分（1 / 3 / 5 分），不要凭感觉。

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| **数据可得性** | 只能拿到部分字段 | 主要字段齐全 | 全部字段 + 结构化 |
| **契约强度** | 私有逆向，无文档 | 半公开 / 未文档化 | 公开 API + 版本号 |
| **失效半径** | 挂了全量停 | 部分字段空 | 单条失败可跳过 |
| **维护成本** | 重新逆向 > 2 小时 | 改选择器 ~30 分钟 | 改配置 ~5 分钟 |
| **合规风险** | 需绕过技术措施 | 需登录 / 需 cookie | 公开数据，无需登录 |

### 2.1 打分示例

**私有 API（biquge 这类）：**

| 维度 | 分数 | 理由 |
|---|---|---|
| 数据可得性 | 5 | 正文完整 |
| 契约强度 | 1 | 私有逆向，token 写死在 JS |
| 失效半径 | 1 | 接口挂了全量停 |
| 维护成本 | 1 | 要重新逆向 token 协议 |
| 合规风险 | 2 | 需绕过来源校验 |
| **总分** | **10** | 快，但脆 |

**HTML 解析（同一站点，如果页面有正文）：**

| 维度 | 分数 | 理由 |
|---|---|---|
| 数据可得性 | 3 | 正文有，结构字段可能缺 |
| 契约强度 | 2 | DOM 结构，无契约 |
| 失效半径 | 3 | 选择器坏了可能只影响部分字段 |
| 维护成本 | 4 | 改选择器即可 |
| 合规风险 | 4 | 抓公开页面 |
| **总分** | **16** | 慢一点，但可维护 |

### 2.2 怎么用总分

| 总分 | 建议 |
|---|---|
| **≥ 18** | 可以作为主路径 |
| **12 ~ 17** | 主路径 + 兜底 + 双跑 |
| **< 12** | 只做兜底，或不用 |

**注意：** 总分低不代表不能用。局面 A（HTML 无数据）里，再低分也得用 API，只是必须配监控和兜底。

---

## 3. 四种默认策略

### 策略 1：公开 API 为主 + HTML 影子校验

**适用：** 有文档、有版本号、字段稳定的公开 API。

```text
主路径：API
兜底：  HTML（只在前 5 条做对比，不全量抓）
必做：  字段差异率监控
```

**为什么还要 HTML：** API 可能返回旧数据或少字段，HTML 是「地面真相」。

---

### 策略 2：私有 API 为主 + HTML 兜底 + 双跑

**适用：** 私有逆向 API，HTML 也能拿到数据。

```text
主路径：API（快）
兜底：  HTML（API 失败时切换）
必做：  双跑对比 + 差异率告警 + 回滚开关
```

**这是最常见的生产形态。** API 省性能，HTML 抗脆弱。

**关键：** 必须能「一键切回 HTML」，否则 API 一挂就全停。

---

### 策略 3：私有 API 唯一 + 浏览器兜底 + 失效监控

**适用：** HTML 无数据，API 是唯一出路（biquge 这类）。

```text
主路径：API
兜底：  Playwright（API 失败时渲染页面）
必做：  token/常量失效监控 + 连续失败告警
```

**这是最脆的形态。** 因为：

- 依赖第三方源（如 `apibi.cc`）；
- 依赖写死的 token 协议；
- 没有 HTML 可以对比。

**必须做的三件事：**

1. 监控 token/常量是否还有效（连续 3 次失败告警）；
2. 准备浏览器兜底（打开阅读页，从 DOM 取正文）；
3. 准备「换源」预案（第三方源挂了怎么办）。

---

### 策略 4：HTML 为主 + 选择器兜底

**适用：** 没有可用接口，或接口风险太高。

```text
主路径：HTML
兜底：  主选择器 → 兜底选择器 → 正文正则
必做：  条数监控 + 字段完整率
```

**低量级首选。** 简单、可控、不依赖第三方。

**什么时候该换 API：**

- 量级上来了（> 1 万条/天）；
- 需要结构化字段（字数/章节数/更新时间）；
- HTML 改版频率明显高于 API。

---

## 4. 决策树

```text
目标数据在 HTML 里吗？
├─ 没有（局面 A）
│   └─ API 唯一 → 策略 3（API + 浏览器兜底 + 失效监控）
│
└─ 有（局面 B）
    ├─ API 是公开契约吗？
    │   ├─ 是 → 策略 1（API 主 + HTML 影子）
    │   └─ 否 ↓
    │
    ├─ 失效半径大吗？（挂了是全量停？）
    │   ├─ 大 → 策略 2（API 主 + HTML 兜底 + 双跑）
    │   └─ 小 → 策略 2 或 4，看维护成本
    │
    └─ 维护成本能接受吗？
        ├─ 能 → 策略 2
        └─ 不能 → 策略 4（HTML 主）
```

---

## 5. 失败分类：兜底不能无脑回退

「API 失败 → HTML」不是万能的。先分类：

| API 失败类型 | 回退 HTML 有用吗 | 正确动作 |
|---|---|---|
| 网络超时 | ✅ | 重试 2 次 → HTML |
| 403 风控 | ⚠️ 大概率也 403 | **停**，冷却，不要连续回退 |
| 404 路径变了 | ✅ | 回退 HTML + 重新发现接口 |
| 200 但字段空 | ⚠️ 可能 API 滞后 | HTML 对比，确认谁更新 |
| 签名失效 | ❌ | 走浏览器，不要硬算 |
| 429 限流 | ⚠️ | 退避，不要立刻换路径 |

对应工作包的 `RiskKind`：

```python
from anti_crawl_kit.risk import RiskKind

result = client.get_json(api_url)

if result.risk.kind is RiskKind.BLOCKED:
    raise                      # 风控：停，不要回退
if result.risk.kind is RiskKind.SIGNATURE_FAILED:
    return fetch_browser()     # 签名：走浏览器
if result.risk.kind is RiskKind.NETWORK_ERROR:
    return fetch_html()        # 网络：回退
if result.status_code == 200 and not data:
    return fetch_html()        # 空数据：对比
```

## 6. 双跑校验

### 6.1 为什么需要

API 最危险的不是「报错」，是「**返回 200 但内容是旧的/少的**」。

没有双跑，你无法发现这种静默失效。

### 6.2 怎么做

不要全量双跑（成本翻倍）。只跑前 N 条：

```python
N = 5

api_items = fetch_api(page=1)[:N]
html_items = fetch_html(page=1)[:N]

diff = compare(api_items, html_items)
```

### 6.3 比什么

| 字段 | 比较方式 |
|---|---|
| 标题 | 完全相等 |
| 作者 | 完全相等 |
| 正文 | 前 100 字哈希 |
| 更新时间 | 允许 1 天内差异 |
| 条数 | 数量差 ≤ 10% |

### 6.4 阈值

```text
差异率 = 不一致字段数 / 总比较字段数

< 5%   → 正常
5~10%  → 记录，观察
> 10%  → 告警：API 可能返回旧数据
> 30%  → 切主路径到 HTML
```

### 6.5 双跑的成本

- 每页多一次 HTML 请求；
- 多 2~5 秒；
- 只在「首屏/首条」做，不要每条都跑。

---

## 7. 监控指标

| 指标 | 计算 | 告警阈值 |
|---|---|---|
| API 成功率 | 200 且字段非空 / 总请求 | < 95% |
| API 与 HTML 差异率 | 不一致字段 / 总字段 | > 10% |
| token/常量失效 | 连续 403 / 解析失败 | ≥ 3 次 |
| HTML 选择器 0 命中 | 主选择器命中数 = 0 | ≥ 3 次 |
| 字段完整率 | 非空字段 / 应有字段 | 比基线掉 10% |
| 平均耗时 | 单次请求 | 比基线涨 2 倍 |

**最小可用监控：** API 成功率 + 差异率 + 连续失败次数。三个都告警，就能覆盖 80% 的失效。

---

## 8. 回滚开关

不要等出事再改代码。留一个环境变量：

```python
import os

SOURCE_MODE = os.getenv("SOURCE_MODE", "api")  # api / html / browser
```

```python
def fetch(page: int):
    if SOURCE_MODE == "html":
        return fetch_html(page)
    if SOURCE_MODE == "browser":
        return fetch_browser(page)
    return fetch_api(page)
```

**出事时的动作：**

```bash
set SOURCE_MODE=html
python collect.py
```

改环境变量，不改代码、不重新打包。

### 8.1 代码实现

`src/anti_crawl_kit/datasource.py` 已经把这套规则落成代码：

```python
from anti_crawl_kit import DataSourcePolicy, fetch_with_fallback

outcome = fetch_with_fallback(
    {
        "api": fetch_api,
        "html": fetch_html,
        "browser": fetch_browser,
    },
    policy=DataSourcePolicy(
        primary="api",
        fallbacks=("html",),
        cross_check=True,
        cross_check_n=5,
        diff_threshold=0.1,
    ),
)

print(outcome.summary())
if outcome.cross_check and outcome.cross_check["alarm"]:
    ...  # 差异率超阈值，API 可能返回旧数据
```

它已经处理了：

| 失败类型 | 动作 |
|---|---|
| `network` / `not_found` / `empty` | 回退下一层 |
| `blocked` / `rate_limited` / `captcha` | **不回退**，直接停 |
| `signature_failed` | 优先插 `browser`，跳过 HTML |
| 主路径成功 | 自动跑双跑对比 |
| `SOURCE_MODE=html` | 只跑 HTML，用于回滚 |

可运行示例：[`examples/12_datasource_fallback.py`](../examples/12_datasource_fallback.py)

## 9. 两个案例

### 9.1 biquge：API 唯一（策略 3）

| 项 | 结论 |
|---|---|
| HTML 有正文吗 | 没有，阅读页是空壳 |
| API 来源 | 前端 `data.js` 里的 AES token 协议 |
| 依赖 | 第三方 `apibi.cc` + 写死的常量 |
| 策略 | API 唯一 + Playwright 兜底 + 失效监控 |

**必须做：**

```text
[ ] 监控 token 协议是否还有效（连续 3 次 403/解析失败 → 告警）
[ ] API 挂了 → 打开阅读页，从 DOM 取正文
[ ] 第三方源挂了 → 有换源预案
[ ] 记录 last_verified 日期
```

**不要做：**

- 不要把「API 能跑」当成「生产可用」；
- 不要在 API 失败时无限重试；
- 不要硬编码 token 常量而不加注释。

### 9.2 纵横：HTML 可用（策略 4 → 2）

| 项 | 结论 |
|---|---|
| HTML 有正文吗 | 有 |
| 量级 | 低 → 策略 4；高 → 策略 2 |
| 策略 | HTML 为主；量级上来再找 API |

**低量级：**

```text
HTML 解析 + 兜底选择器 + 条数监控
```

**高量级（> 1 万条/天）：**

```text
API 为主 + HTML 兜底 + 双跑
```

**判断标准：** 不是「API 一定更好」，是「量级带来的性能收益 > 维护成本」。

## 10. 落地清单

新接一个平台，按这个顺序做：

```text
[ ] 判断局面：HTML 有没有数据？（A / B / C）
[ ] 局面 B 才打分：五维 × 每条路径
[ ] 选策略：1 / 2 / 3 / 4
[ ] 两条路径都实现（策略 2/3）
[ ] 失败分类：接 RiskKind
[ ] 双跑校验：前 5 条 + 差异率
[ ] 监控：成功率 / 差异率 / 连续失败
[ ] 回滚开关：SOURCE_MODE
[ ] 失效演练：手动关掉主路径，看兜底是否生效
[ ] 记录 last_verified
```

**最后一项最重要：** 没有演练过的兜底，等于没有兜底。
