# 10 · 采集器工程架构

> 目标不是「今天能跑」，而是「三个月后平台改版，还能在半小时内修好」。
>
> 本文提炼自一套跑了半年、覆盖十几个平台的生产采集系统。
> 这里的每条结构，都是被线上事故逼出来的。

---

## 1. 六段式生命周期

一个采集器不要写成一个 800 行的 `run()`。按阶段拆，每段有明确的输入、输出和失败行为：

```text
prepare → auth → fetch → parse → enrich → persist
```

| 阶段 | 职责 | 失败时 |
|---|---|---|
| **prepare** | 读配置、校验参数、创建 session、检查环境（Chrome 版本/代理/profile） | 直接退出，不重试 |
| **auth** | 检测登录态、等验证码、拿签名密钥、提取 cookie | 可等人（双时钟）；超时退出 |
| **fetch** | 调接口 / 开页面 / 滚动 / 翻页 | 按策略链降级；验证墙硬停 |
| **parse** | 把原始响应转成标准字段 | 单条失败跳过并记录，不整体失败 |
| **enrich** | 补详情、补统计、补作者 | 可选；失败保留列表字段 |
| **persist** | 去重、落盘、上报 | 幂等；失败可重放 |

### 为什么必须拆

- **可中断**：`fetch` 的循环里能检查取消信号，不用等整条链路跑完。
- **可降级**：`fetch` 失败时，`parse` 不用重写。
- **可诊断**：日志能定位到「哪一段、哪一步、哪条数据」。
- **可测试**：`parse` 可以喂固定 JSON 做单测，不需要浏览器。

### 最小骨架

```python
class Collector:
    def run(self, task: dict) -> dict:
        ctx = self.prepare(task)          # 配置、session、环境
        self.auth(ctx)                    # 登录、验证码、签名
        raw = self.fetch(ctx)             # 接口 / 页面 / 滚动
        items = self.parse(raw)           # 原始 → 标准字段
        items = self.enrich(items, ctx)   # 可选补全
        return self.persist(items)        # 去重、落盘

    # 每一段都可以单独测试
```

**判断标准：** 如果 `run()` 超过 60 行，说明阶段没拆干净。

## 2. 策略链：同一份数据至少留两条路

> 选型（API vs HTML、五维打分、双跑校验、回滚开关）见
> [`19-数据源选型与兜底.md`](19-数据源选型与兜底.md)。

不要写「只有一个接口」的采集器。接口会变、会加签、会限流。

### 2.1 标准降级链

```text
L0  JS 包找接口       tools/js_api_hunt.py（HTML 空壳时）
L1  HTTP 直连         curl_cffi / AntiRiskHttpClient
L2  SSR 全局状态      __INITIAL_STATE__ / __NEXT_DATA__ / RENDER_DATA
L3  XHR 响应拦截      page.capture_responses()
L4  DOM 解析          选择器 + 兜底选择器
L5  截图 OCR          仅 Canvas / 字体混淆，最后手段
```

### 2.2 降级矩阵

| 触发条件 | 从哪降到哪 | 注意 |
|---|---|---|
| 接口 403 / 429 | L1 → L3 | 先冷却，不要立刻重试 |
| 接口返回 `signature_failed` | L1 → L3 | 不要自己逆签名 |
| 接口 200 但字段为空 | L1 → L3 / L4 | 可能是字段改名 |
| SSR 状态不存在 | L2 → L3 | 平台可能改成纯 XHR |
| DOM 选择器 0 命中 | L4 → L3 / L5 | 先确认是不是改版 |
| 页面是 Canvas | L4 → L5 | 截图 OCR |

### 2.2.1 升级要证据驱动，不要固定顺序

固定顺序「API 失败就上浏览器」有两个问题：

- API 失败可能只是网络抖动，上浏览器是浪费；
- 403 时上浏览器大概率还是 403。

成熟做法是**先分类证据，再决定升级到哪一层**：

| 证据 | 升级动作 |
|---|---|
| 空壳页（HTML 有，目标节点空） | 下一层渲染 |
| TLS 阻断 / 握手错误 | 换 HTTP 客户端或浏览器 |
| WAF 页面（Cloudflare/DataDome） | 浏览器，或停 |
| 传输错误（超时/DNS） | 重试，不升级 |
| 403 / 429 | 停，不升级 |
| 200 但字段空 | 回退另一数据源，不升级 |

**统一结果结构**（借鉴 omk-crawling 的 `CrawlResult`）：

```python
{
    "ok": False,
    "tool": "curl_cffi",
    "status": "blocked",
    "detection": "cloudflare",
    "stop_reason": "blocked",
    "attempts": [...],
}
```

关键：**不要把拒绝伪装成成功**。失败了就写清 `stop_reason`，
下游才能决定是重试、换路径，还是告警。

**代码：** [`src/anti_crawl_kit/empty_shell.py`](../src/anti_crawl_kit/empty_shell.py)
—— `detect_empty_shell(html, selector=...)` 判断空壳；
[`datasource.py`](../src/anti_crawl_kit/datasource.py) 负责按策略回退。

`fetch_with_fallback` 的返回对象直接带这些字段：

```python
outcome = fetch_with_fallback({"api": fetch_api, "html": fetch_html})

outcome.ok            # False
outcome.stop_reason   # "blocked" / "captcha" / "empty" / "no_fetcher" ...
outcome.detection     # "cloudflare" / "datadome" / ""（识别到的 WAF）
outcome.elapsed_ms    # 整条链路耗时
outcome.attempts      # 每一层的 source / risk / detection / elapsed_ms
outcome.summary()     # 一行文本，直接写日志
```

### 2.3 策略执行器

不要把降级写成嵌套 `if/else`。用有序列表 + 结果记录：

```python
from anti_crawl_kit.strategy import run_strategies

results = run_strategies([
    ("initial_state", lambda: extract_state(page)),
    ("dom",           lambda: extract_dom(page)),
    ("universal",     lambda: extract_universal(url)),
], stop_on_first_items=True)

for r in results:
    if r.items:
        log(f"命中策略 {r.name}，{len(r.items)} 条")
        break
else:
    log("全部策略为空，需要人工确认是否改版")
```

**关键：** 每条策略的结果都要记录 `name / ok / error`，不要只返回最终列表。否则出问题时不知道是哪条挂了。

### 2.4 给结果打来源标记

每条数据加 `source_strategy`：

```python
item["source_strategy"] = "api" | "ssr" | "xhr" | "dom" | "universal"
```

上线后统计各策略占比：

- 某个策略占比突然从 90% 掉到 0 → 大概率改版；
- 兜底策略占比从 5% 涨到 80% → 主策略已失效，只是被兜底掩盖。

## 3. 错误模型：不要用异常表示业务状态

`try/except Exception: pass` 是采集器最大的技术债。

### 3.1 七类风险，七种动作

| 类型 | 典型信号 | 动作 |
|---|---|---|
| `OK` | 200 + 正常 JSON | 继续 |
| `LOGIN_REQUIRED` | 401 / 「请登录」/ 跳登录页 | 等人登录；批量阶段硬停 |
| `CAPTCHA` | 验证码 DOM / URL / 标题 | **硬停**，截图 + 通知，不重试 |
| `RATE_LIMITED` | 429 / 「请求过于频繁」 | 退避 + 降速；连续两次换时间段 |
| `BLOCKED` | 403 / 412 / 418 / 521 | 冷却 30~60 分钟，不要硬刚 |
| `SIGNATURE_FAILED` | `a_bogus` / `w_rid` / `-352` | 不要自己算；走浏览器执行页面函数 |
| `NETWORK_ERROR` | 超时 / DNS / SSL | 有限重试（2~3 次），指数退避 |

### 3.2 判定优先级

先判 HTTP 状态，再判业务 code，再判页面特征，最后判字段是否为空。

```python
def classify(status, body_text, url, data):
    if status == 429:                    return RATE_LIMITED
    if status in (401,):                 return LOGIN_REQUIRED
    if status in (403, 412, 418, 521):   return BLOCKED
    if "验证码" in body_text or "安全验证" in body_text:
                                         return CAPTCHA
    if isinstance(data, dict) and data.get("code") in (-352, -412):
                                         return SIGNATURE_FAILED
    if status >= 500:                    return NETWORK_ERROR
    return OK
```

### 3.3 不要吞异常

```python
# 反例
try:
    items = extract(page)
except Exception:
    items = []

# 正例
try:
    items = extract(page)
except ChallengeDetected:
    raise                      # 验证墙必须往上抛
except BrowserClosedError:
    raise                      # 用户关窗必须往上抛
except Exception as exc:
    log.warning("提取失败，返回空: %r", exc)
    items = []
```

**规则：验证墙和关窗，永远不要被 `except Exception` 吞掉。**

## 4. 会话与资源

### 4.1 一个任务一个会话

```text
任务开始 → 创建 session → 登录/复用 profile → 采集 → 关闭 session
```

不要在模块级创建全局 `browser` / `page`。全局单例会带来：

- 上一个任务的 cookie 串到下一个任务；
- 上一个任务的异常状态污染下一个任务；
- 并发时互相覆盖。

### 4.2 profile 按「平台 + 账号」隔离

```text
profiles/{platform}/{account_alias}/
```

- 同一平台多账号 → 一个 alias 一个目录；
- 采集和发布 → 尽量分开目录（创作者中心和网页版会话经常不通用）；
- **不要**用 `storage_state` 跨 profile 导入导出，平台风控会拒绝。

### 4.3 关窗即取消

任何等待循环（登录、验证码、滚动、翻页）入口都要检查存活：

```python
from anti_crawl_kit.alive import ensure_alive

for round_no in range(max_rounds):
    ensure_alive(page, label="list")
    ...
```

**注意：** `page.is_closed()` 会假阴性。浏览器进程被杀后 CDP 断连，它可能返回 `False`。必须用轻量 `evaluate` 探针确认存活。

### 4.4 资源回收

| 资源 | 回收方式 |
|---|---|
| 浏览器 context | `context.close()`，失败再 `browser.close()` |
| driver 子进程 | 任务结束检查 `--type=` 子进程，父进程死则清理 |
| 下载临时文件 | `.part` 文件在 `finally` 里删 |
| 截图/HTML 快照 | 按数量保留（如最近 20 组），自动清理旧的 |

## 5. 配置与常量

### 5.1 接口常量集中管理

```python
# constants.py
# last_verified: 2026-11-04
POPULAR_URL = "https://api.example.com/x/web-interface/popular"
DETAIL_URL  = "https://api.example.com/x/web-interface/view"
```

规则：

- 所有接口地址放一个文件，不要散落在业务逻辑里；
- 每个常量带 `last_verified` 日期；
- 平台改版时，只改这个文件。

### 5.2 选择器配置化

```yaml
name: demo
card_selector: "section.note-item"
fallback_selectors:
  - "div.note-item"
  - "[data-testid='note-item']"
fields:
  title: {selector: "h3", attr: text}
  url:   {selector: "a.cover", attr: href}
```

**兜底选择器不是可选项。** 平台改版通常只改一层 class，有兜底就能多活一周。

### 5.3 超时用环境变量

```python
CAPTCHA_WAIT = int(os.getenv("AC_KIT_CAPTCHA_WAIT", "100"))
LOGIN_WAIT   = int(os.getenv("AC_KIT_LOGIN_WAIT", "200"))
NAV_TIMEOUT  = int(os.getenv("AC_KIT_NAV_TIMEOUT", "30000"))
```

不要写死 `sleep(200)`。生产环境调参不应该改代码。

## 6. 可观测性

### 6.1 每阶段一条日志

```text
[prepare] profile=profiles/xhs/acc1 chrome=131 代理=已配置
[auth]    登录态=有效 method=cookie+dom
[fetch]   策略=api 第1页 20条 耗时=0.8s
[parse]   20条 字段完整率=98% 缺失=play
[enrich]  补详情 20/20
[persist] 新增=18 去重=2 输出=output/xhs.json
```

出问题时，一眼能看出是哪一段。

### 6.2 字段追踪

不要只记录「采到 20 条」，要记录「每个字段从哪来、缺了没」：

```python
tracker.track("fansNum", value=fans, raw_value=raw.get("fansNum"),
              source="GET /my/dynamic_num", item_id=uid)
```

缺失判定要区分：

| 值 | 含义 | 是否缺失 |
|---|---|---|
| `None` | 接口没返回 | ✅ |
| `""` | 空字符串 | ✅ |
| `0` | 真的是 0 | ⚠️ 看业务 |
| `False` | 有效布尔值 | ❌ |
| `"default"` / `"未知"` | 占位符 | ✅ |

**不要用 `0` 表示「没有」。** 用 `None`，否则无法区分「播放量真的是 0」和「没采到」。

### 6.3 现场快照

验证墙/解析失败时，保存三件套：

```text
output/challenge/20261104-153012_captcha.png
output/challenge/20261104-153012_captcha.html
output/challenge/20261104-153012_captcha.json   # url/reason/title/时间
```

没有现场，事后只能猜「是验证码还是改版」。

### 6.4 四个核心指标

| 指标 | 告警阈值 |
|---|---|
| 条数 | 连续 3 次为 0 → 告警 |
| 字段完整率 | 比基线掉 10% → 告警 |
| 验证码命中率 | 单账号一天 > 2 次 → 降速/换 IP |
| 平均耗时 | 比基线涨 2 倍 → 查网络/风控 |

## 7. 反模式清单

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| `time.sleep(5)` 等渲染 | 快页面浪费 5s，慢页面还是不够 | `wait_for_stable_text` / `wait_for_selector` |
| `while True` + 重试 | 验证墙越撞越深，账号被封 | 有限重试 + 硬停 |
| `except Exception: pass` | 问题被静默吞掉，线上「成功但 0 条」 | 分类捕获，验证墙/关窗必须抛 |
| 全局单例 browser | 任务串号、并发冲突 | 一任务一会话 |
| 硬编码 UA | 与真实 Chrome 版本矛盾 | 用系统 Chrome 默认 UA |
| 用 `0` 表示缺失 | 无法区分「真是 0」和「没采到」 | `None` |
| 接口只留一条路 | 改版即死 | 策略链 + 兜底 |
| 选择器散落各处 | 改版要改 10 个文件 | 集中配置 |
| 无停止条件的滚动 | 无限加载/死循环 | 连续 N 轮无新增即停 |
| 日志只打「开始/结束」 | 出问题无法定位 | 每阶段一条 |
| 默认开 `block_resources` | 验证码/二维码被拦，登录永远等不到 | 默认 `False`，登录阶段必须 `False` |
