## 3. 这次验证暴露的六个坑

### 3.1 评论参数是 `limit`，不是 `count`

用 `count=20` 时接口返回 `err_no=0, data=[], count=0`——**不报错、不 4xx，
只是空列表**。这是最典型的静默失效：如果只看「请求成功」，会误判
「这篇文章没有评论」。

改成 `limit=20` 后正常返回。对应教训：`RunReport` 的 `actual_count=0`
必须判 `empty`，不能判 `ok`。

### 3.2 文章详情必须带 `client_type=2608`

不带时返回 `err_no=2 参数错误`；GET 路由直接 404。

### 3.3 GET 用户接口必须用 `get_json`

`AntiRiskHttpClient.get_text()` 不会解析 JSON（`data=None`）。
第一次探测时用 `get_text` 拿用户资料，看起来「200 但没数据」，
实际是解析层用错了。

### 3.4 签名不是所有接口都强制

浏览器里文章详情、v1 评论请求都带 `a_bogus` + `verifyFp/fp`。
实测 v1 评论在参数正确（`limit`）时可以纯 HTTP；如果后续收紧，
走浏览器 XHR 拦截（L3）或回放签名 URL。

**拿到接口 ≠ 能纯 HTTP**，必须做参数/签名剥离测试。

### 3.5 评论数的口径

文章详情里的 `comment_count` 包含主评论 + 回复。
`comment/list` 返回的是主评论（`reply_infos` 里嵌套回复）。
本次选中文章声明 114 条，抓到 51 条主评论，`has_more=False`，口径一致。

### 3.6 cookie 身份校验

带 cookie 调 `GET /user_api/v1/user/get`（不传 `user_id`）返回当前登录用户。
本次返回的账号与目标 URL 一致。

这条可以用来做账号监控的前置检查：cookie 是否过期、是否串号。
如果只调 `?user_id=`，拿到的是公开主页，不能证明 cookie 属于该账号。

## 4. 对工具包的改进（已落地）

这次验证后补了两个通用步骤，并把评论检查固化成了配方：

1. **`http_request` 步骤**：支持 POST、`json`、`headers`、`cookies_env`，
   解决「平台核心接口是 POST + 需要 cookie」的配置化问题。
2. **`assert_non_empty` 步骤**：对 `data`/`comments`/`count` 做非空断言，
   把「成功但 0 条」变成 recipe 失败。
3. **掘金评论检查配方**：`examples/recipes/juejin_comment_check.yaml`。
   实测：正确 `limit` → `done`（第一页 20 条）；改成 `count` → `failed`，
   返回 `data=[]`，错误信息提示「检查 count vs limit」。

## 5. 安全与合规

- cookie 只存在于临时脚本/进程环境，**没有写入仓库、报告或日志**。
- 原始 `data.json` 含真实用户名/评论，已删除，不随开源版本分发。
- 报告只保留聚合数字和匿名化样本。
- 只采集公开可见内容 + 用户本人账号；未做发布、点赞、关注等写操作。
- 请求间隔 0.35s，未触发 403/429。
