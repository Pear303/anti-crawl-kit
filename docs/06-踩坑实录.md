## 案例 1：CDP 首导航空白转圈（2026-08-20）

**现象**
手动浏览采集打开小红书，标签页一直空白转圈，`goto` 却返回成功；
必须手动 Ctrl+Shift+R 硬刷新才能加载。

**根因**
patchright 1.61.2 面向 Chromium 150，系统 Chrome 自动升级到 151。
版本 gap 导致 CDP 首次导航的完成事件丢失；叠加当天网络故障（SSL 重置 /
DNS 失败 / 超时），页面停在空白。

**修复**
1. 升级 patchright 1.62.1（对齐 Chromium 151）。
2. CDP 接管后主动检查 `document.readyState`，未达 `interactive/complete`
   就 reload（最多 2 次，每次 7s）。
3. 客户端心跳上报 Chrome 版本，服务端超过兼容上限时推送告警横幅。

**教训**
- **patchright 与 Chrome 大版本必须严格同步**，Chrome 自动更新不可控，
  升级 patchright 是唯一对齐手段。
- 任何「接管外部浏览器」的链路都要有首导航自愈，不能假设 `goto` 成功 = 页面可用。
- 版本兼容要可观测（上报 + 告警），不要等用户报障。

## 案例 2：关窗后空烧 600 秒（2026-08-22）

**现象**
用户手动关闭采集浏览器窗口，任务没有结束：继续等验证码 100s + 登录 200s，
多关键词场景每个关键词都重开一个新窗口，直到 30 分钟全局超时。

**根因**
所有等待循环都没有「浏览器是否还活着」的探测。

**修复**
新增 `anti_risk/browser_alive.py`：

```python
def is_page_closed(page):
    # 1. 快路径：is_closed() True 即死
    # 2. 探针：evaluate("() => 1") 确认存活
    ...
```

接入 6 个等待点：主循环、关键词 runner、登录守卫、监控器、CDP 浏览主循环。

**关键细节（实测）**
浏览器进程被杀后 CDP 断连，Playwright 收不到 `targetDestroyed` 事件，
`page.is_closed()` **假阴性返回 False**。所以：

- `is_closed()` 只能作「确认死亡」的快路径；
- 存活必须由轻量 `evaluate` 探针确认（1-5ms，对秒级轮询无感）。

**教训**
- 任何可能长达几分钟的等待循环，入口必须探测存活。
- 不要相信单一 API 的「存活」语义，尤其是跨进程/跨 CDP 的场景。
- 探测要区分「确认死亡」和「确认存活」，不能对称处理。

## 案例 3：`destroyed` 误判活窗口（2026-08-24）

**现象**
修复关窗探测后，登录成功整页跳转 / 验证码通过重新导航的瞬间，
任务偶发误报「浏览器已关闭」。

**根因**
patchright 在页面导航期间 `evaluate` 会稳定抛：

```
Execution context was destroyed, most likely because of a navigation
```

而关闭特征里包含了 `"destroyed"`，于是活窗口被误判为死亡。

**修复**

```python
# 只收 closed / target
_CLOSED_MARKERS = ("closed", "target")
```

真关窗的 `TargetClosedError`（"Target page, context or browser has been closed"）
和 driver 断连（"Connection closed while reading from the driver"）都含这两个词；
导航期间的 `destroyed` 不再误判。漏判最多延迟一轮轮询，无害。

**教训**
- 异常特征词要「窄」，不要用宽泛词（`destroyed` / `connection` / `websocket`）。
- 误杀活任务的代价 > 晚一轮发现死窗口。
- 加回归用例：`test_navigation_destroyed_error_not_misjudged`。

## 案例 4：登录窗「系统繁忙」（2026-09-10）

**现象**
桌面端自动化登录窗打开各平台创作者页都提示「系统繁忙」或极卡，
同一台机器手工 Chrome 打开完全正常。

**排查**
后端健康、Chrome/patchright 版本、本机资源、profile 锁、PyInstaller 残留
全部排除。

**根因**
桌面端登录链路（sidecar JS）是**裸 patchright**：

- 全目录搜 `addInitScript` / `stealth` = 0
- Chromium args 只有 2 个（`--disable-blink-features` + `--start-maximized`）
- 而 Python 采集侧有 `STEALTH_JS` + 完整 30+ 参数

两套实现，防风控措施长期只在 Python 侧。

**修复**
新建 `desktop-tauri/sidecar/lib/config/stealth.js`，与
`anti_risk/stealth.py::STEALTH_JS` 同源；`shared.js` 新增
`LOGIN_CHROMIUM_ARGS`（= Python `CHROMIUM_ARGS` 有头全集）；
三条降级启动路径统一注入 stealth + 补 `ignoreHTTPSErrors`。

**教训**
- **新增/嫁接功能必须对齐项目已有反风控设施。**
- 同一能力存在两套实现（Python / JS）时，必须显式互相注释「两侧同步」。
- 手工浏览器正常 ≠ 自动化环境正常：手工浏览器通常已有长期登录态，不走登录接口。

## 案例 5：反爬水印污染正文（2026-08-06）

**现象**
公众号 / 头条 / CSDN 的文章正文里混入大量 `word word word...` 和
`mmMwWLliI0fiflO` token，落库后前端显示异常。

**根因**
平台在自动化浏览器渲染的 DOM 内注入水印/蜜罐文本，用于检测复制粘贴和自动化。

**修复**

```python
text = re.sub(r"[\u200b\u200c\u200d\u200e\u200f\u2060\ufeff]", "", text)
text = re.sub(r"(?:mmMwWLliI0fiflO(?:&\d+)?)+", "", text, flags=re.I)
text = re.sub(r"(?:word[\s\u200b...]*){5,}", "", text, flags=re.I)
```

接入所有正文抓取、DOM 提取、关键词检索 `clean_html`、Jina Reader 兜底、
后端分析前清洗。

**教训**
- 反爬不只有「拦截」，还有「投毒」。
- 清洗必须是纯文本后处理，不能触发任何额外请求/升级。
- 大小写、连续 token、零宽字符变体都要覆盖。

## 案例 6：新平台采集全空，但任务「成功」（2026-08-20）

**现象**
简书 / 掘金 / 百家号对标博主采集任务 2-4 秒完成，`item_cnt=0`；
掘金采到 10 条但 profile 全空、URL 是首页随机文章。

**根因**
`runner.py::_extract_entry_value()` 只写了 7 个老平台分支，
新增的简书/掘金/百家号没有分支，最后 `return ""` → 入口参数为空 →
采集器拿不到目标博主 → 空结果。

**修复**
1. 补三个平台的 URL 提取分支。
2. 掘金滚动 3→15 次，更新失效选择器，补详情页元数据。
3. 百家号改用 `.feed-item` 卡片属性（SPA 点击绑定，`<a href>` 已不存在）。
4. 简书改用 `AntiRiskHttpClient` 绕过反爬。

**教训**
- **新增平台要同时改三处**：能力注册表、采集器、入口参数提取。
- 「任务成功 + 0 条」比「任务失败」更危险，必须把 0 条当异常。
- SPA 页面不要假设 `<a href>` 存在，数据可能在 data 属性或 JS 对象里。

## 案例 7：profile 缓存 3GB，登录窗卡十几秒（2026-09-10）

**现象**
登录窗/采集启动越来越慢，实测单 profile 487MB，总缓存 3GB。

**根因**
Chrome 持久化 profile 的 `Cache` / `Code Cache` 无限累积，
冷启动要加载校验缓存。

**修复**
`CHROMIUM_ARGS` 加 `--disk-cache-size=268435456`（256MB，LRU 自动淘汰）；
`prune_profile_cache` 保留作兜底（总量 > 400MB 才清）。

**教训**
- 不要用「清空缓存」解决慢：首访全冷加载反而更慢。
- LRU 上限是正解：热缓存保留、总量受控。
- 持久化 profile 必须纳入容量治理。

## 案例 8：driver 进程泄漏（2026-08-13）

**现象**
新榜采集（无系统浏览器环境）每次失败泄漏 10 个 ~133MB 的 node driver 进程。

**根因**
`sync_playwright().start()` 已 spawn `run-driver`，后续 `launch` 失败抛异常；
`with` 语句不会调用 `__exit__`（因为 `__enter__` 未正常返回），driver 没 stop。

**修复**
`__enter__` 包 try/except，失败时 `_cleanup_after_failed_enter()`：
关 page/context/browser + `playwright.stop()`。

**教训**
- 资源清理要覆盖「构造失败」路径，不能只写在 `__exit__`。
- 打包/分发前要检查进程表，不能只看 Python 层是否退出。

## 案例 9：GBK 控制台吞掉已成功的结果（2026-08-07）

**现象**
快手视频拆解已拿到直链，但最终回传「缺少可下载的 video_url」。
日志里没有任何异常。

**根因**
标题含 `\xa0`，`print(title)` 在 Windows GBK stdout 抛 `UnicodeEncodeError`；
外层 `except Exception` 把「已拿到的结果」整体吞掉。

**修复**
1. 所有调试 `print` 改 `_safe_print`（捕获 `UnicodeEncodeError`）。
2. 新增 `safe_print.py`，启动时全局替换 `builtins.print`。
3. 冒烟脚本日志只用 `[OK]/[WARN]/[FAIL]`，禁用 emoji。

**教训**
- `print` 也会抛异常，且常被宽泛 `except` 吞掉。
- Windows 控制台编码是生产环境的一等公民。
- 诊断日志改用 `repr()` 避免不可见字符。

## 案例 10：全仓 import 替换漏掉 backend（2026-08-10）

**现象**
playwright → patchright 切换后，服务端仍有旧副本直接 `import playwright`，
部署前排查才发现。

**根因**
替换只扫了 `packages/`，没扫 `backend/app/services/benchmark/collectors/`。

**修复**
全仓 grep `playwright`，对齐 re-export（提交 e9df630）。

**教训**
- 依赖替换必须全仓扫描（含 backend、scripts、tests、desktop）。
- 部署前做一次「运行时 import 图」验证，不要只跑单测。
- 盲点往往在「看起来不相关」的目录。

## 案例 11：资源拦截把验证码/二维码一起拦了

**现象**
开启 `block_resources=True` 后，登录二维码不显示，滑块图加载不出来。

**根因**
默认拦截 `image` 类型，二维码和滑块图都是图片。

**修复**
登录/验证码阶段强制 `block_resources=False`；
需要拦截时加白名单域名。

**教训**
性能优化不能无条件全局开启；要按阶段区分。
实测资源拦截对加载速度提升有限，收益远小于风险。

## 案例 12：CSDN 改版，昵称变成 ID（2026-08-11）

**现象**
博主主页采集结果「昵称 = 用户 id」，头像/简介/统计全空。

**根因**
CSDN 博主主页 DOM 改版，旧选择器全部失效，代码 fallback 到 URL 里的 username。

**修复**
更新 `.user-profile-head-name > div:first-child` 等新选择器，
旧选择器保留兜底；同步更新 `_page_has_content` 与监控器解析。

**教训**
- fallback 到「看起来像数据」的字段（URL 里的 id）会掩盖故障。
- 页面改版要同时改采集器 + 监控器 + 内容检测三处。
- 用真实 HTML fixture 做回归测试，别用 mock 的假 DOM。
